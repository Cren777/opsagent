# 告警处理流程

## 标准处理流程

```
收到告警 
  → 确认告警级别（critical/warning/info）
    → 初步判断影响范围
      → 执行排查步骤
        → 定位根因
          → 实施修复
            → 验证修复效果
              → 关闭告警/记录总结
```

## 按告警级别响应

### Critical（严重）- 15分钟内响应
1. 立即通知 on-call 人员
2. 判断是否为业务中断
3. 如是：先恢复业务，再排查原因
4. 优先级：恢复服务 > 排查根因 > 修复优化

### Warning（警告）- 1小时内响应
1. 记录告警到工单系统
2. 分析趋势（是否持续恶化）
3. 制定处理计划
4. 非紧急可排期处理

### Info（信息）- 24小时内评估
1. 评估是否需要关注
2. 纳入日常巡检

## 典型告警处理流程

### CPU使用率过高
```
1. 确认受影响服务器和服务
   ssh web-01 && top
2. 找到高CPU进程
   ps aux --sort=-%cpu | head -10
3. 分析该进程
   - 应用进程 → 检查应用日志
   - 数据库进程 → 检查慢查询
   - 系统进程 → 检查系统负载
4. 临时措施
   - 限流/降级
   - 扩容（K8s HPA）
5. 根因修复
   - 优化代码
   - 调整JVM参数
```

### 磁盘空间不足
```
1. 确认磁盘使用情况
   df -h
2. 定位大文件
   du -ah / | sort -rh | head -20
3. 清理（按优先级）
   a. /tmp 临时文件
   b. 过期日志
   c. 旧备份文件
   d. Docker镜像/容器
4. 预测剩余时间
   根据增长速率计算还能撑多久
5. 扩容计划
   LVM扩展 / 申请新磁盘
```

### 服务不可用
```
1. 确认服务状态
   systemctl status <service>
2. 查看服务日志
   journalctl -u <service> -n 100
3. 检查依赖
   - 端口是否被占用
   - 配置文件是否正确
   - 依赖服务是否正常
4. 尝试重启
   systemctl restart <service>
5. 回滚（如有最近变更）
   回滚至上一个已知良好的版本/配置
```
